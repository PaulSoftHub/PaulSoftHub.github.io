AI PE-OS / KNOWLEDGE 03

Prompt Development Request (PDR)

A structured method for converting a real business or workflow requirement into a clear prompt-development request before designing the runtime prompt.

01 — PDR FUNDAMENTALS

What Is a Prompt Development Request?

A Prompt Development Request (PDR) is a structured starting point for developing an AI prompt.

Instead of immediately writing a prompt, the PDR first defines the problem, purpose, expected outcome, scope, inputs, constraints, users, and other requirements that should be understood before prompt development begins.

The PDR therefore acts as a bridge between a real requirement and the technical design of a prompt.

02 — WHY PDR?

Why Start With a PDR?

Clarify the Requirement

A PDR forces the underlying requirement to be understood before prompt-writing begins.

Define the Objective

The intended result is explicitly identified rather than being left implicit.

Reduce Rework

Early clarification can reduce unnecessary prompt revisions caused by incomplete requirements.

Establish Scope

The PDR identifies what the prompt should address and what falls outside its scope.

Define Success

Expected outcomes and acceptance criteria can be identified before development starts.

Create a Development Record

The PDR provides documented context for why the prompt is being developed and what it is expected to accomplish.

03 — REQUIREMENT ANALYSIS

From Real Requirement to PDR

Prompt development should begin with the problem, not with the prompt itself.

01

Identify the Problem

What real business, management, productivity, analysis, or workflow problem needs to be solved?

02

Define the Objective

What should the AI-assisted workflow accomplish when the requirement is successfully addressed?

03

Identify the Inputs

What information, reports, documents, data, or user instructions will be available?

04

Define the Expected Output

What should the AI produce, and in what form should the result be delivered?

04 — PDR STRUCTURE

Core Components of a PDR

PDR ID

A unique identifier that allows the development request to be referenced and tracked.

Title

A concise name describing the proposed prompt or AI-assisted workflow.

Business Requirement

The underlying problem or operational need that creates the reason for development.

Objective

The specific result the proposed AI workflow should achieve.

Scope

The boundaries of the proposed solution, including relevant inclusions and exclusions.

Users

The intended users or stakeholders who will interact with or depend on the workflow.

Inputs

The information and resources expected to be available when the workflow runs.

Outputs

The required results, information, decisions, summaries, or other deliverables.

Constraints

Rules, limitations, exclusions, dependencies, confidentiality requirements, or other boundaries.

Acceptance Criteria

Conditions that can be used to determine whether the developed solution meets the requirement.

06 — IMPORTANT DISTINCTION

PDR Is Not the Runtime Prompt

PDR

Development Definition

The PDR explains why the prompt is needed, what problem it should solve, what the expected outcome is, and what requirements must be considered.

PROMPT

Execution Instruction

The runtime prompt contains the instructions that the AI system actually follows during execution.

07 — NEXT DEVELOPMENT STAGE

From PDR to Prompt Specification

Once the PDR clearly defines the requirement, the next step is to translate those requirements into a detailed Prompt Specification.

The specification describes how the intended prompt should behave, including its workflow, rules, inputs, outputs, dependencies, quality requirements, and other implementation details.

This separation allows the requirement to be understood first and the execution design to be developed second. 

PDR
 │
 ├── Why is it needed?
 ├── What problem does it solve?
 ├── What is the objective?
 ├── What is the scope?
 ├── What are the inputs?
 ├── What are the outputs?
 ├── What are the constraints?
 └── How will success be measured?
        │
        ▼
Prompt Specification
        │
        ▼
Runtime Prompt

08 — PRACTICAL VALUE

Why This Matters in Real Work

Better Requirement Understanding

The development team can understand the intended outcome before designing the AI instructions.

Better Prompt Quality

Clear requirements provide stronger foundations for designing the runtime prompt.

Easier Review

Stakeholders can review the proposed requirement before the prompt is implemented.

Better Traceability

The relationship between requirement, PDR, specification, prompt, and UAT can be documented.

Controlled Improvement

Future changes can be evaluated against the original requirement and acceptance criteria.

Reusable Methodology

A consistent PDR approach can be reused across different AI-assisted projects and workflows.

10 — KEY TAKEAWAYS

What to Remember

Start With the Requirement

Do not begin with prompt wording before understanding the problem to be solved.

Define the Outcome

A useful PDR makes the intended result explicit.

Define the Boundaries

Scope and constraints help prevent uncontrolled expansion of the requirement.

Define Acceptance

The development team should know how the final solution will be judged.

Separate Requirement From Execution

The PDR defines the development need; the runtime prompt defines AI execution behavior.

Maintain Traceability

Keep a clear relationship between requirement, PDR, specification, prompt, testing, and improvement.
